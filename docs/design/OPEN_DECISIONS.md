# Cerberus — Open Decisions

## Prioritized Decisions

### FOUNDATIONAL MATH (must lock before any balance work)

| Priority | Decision | Why it matters | Recommended default |
|---|---|---|---|
| P0 | Rewrite the skill XP curve. The live formula in SkillManager.calculateRequiredXpForNextLevel is currentLevelXP = 100, doubled per level = 100 * 2^(level-1). This int overflows around level 25 (2^31) and is mathematically unreachable long before 100. Pick a curve shape (proposed hybrid polynomial: cost(L) = BASE*L^EXP + LINEAR*L with BASE=75, EXP=1.85, LINEAR=40, ~19M cumulative XP to 100), and decide whether all 34 skills share one curve or utility/gathering skills cap faster (lower EXP). | Every skill levels by this formula. As written it overflows to negative/garbage and bricks progression past the low 20s; nothing about mob XP rewards, pity timers, or the badge can be tuned until the curve is real. This is the single rescaling lever for the whole grind. | Adopt the hybrid polynomial as a long (not int) accumulator; one unified curve for v1 to avoid 34 separate tunings, with a single per-category EXP knob reserved in config for later. Store cumulative-XP-to-level in a lookup table built at load, not recomputed per add. |
| P0 | Define the player power ceilings: max HP from skills (proposed ~1,000) / with gear (~1,500), and the max stacked combat damage multiplier (proposed 6.0x clamp in CombatSkillProcessor). Then kill the FirstAidSkill runaway — line 27 grants level*1500 HP/level (=150,000 HP at level 100) and line 31 grants level*1000 regen/level. This dead/extreme code must be capped or rewritten to ScalingFormula. | The entire mob HP/damage curve is balanced against the player ceiling. With FirstAid alone granting 150k HP, no mob (capped at 5000) can ever threaten a player, and PvP and the defense-bar math are meaningless. The offensive clamp likewise defines time-to-kill. These two numbers are THE anti-power-creep anchors. | Lock ~1,000 HP skills / ~1,500 with gear and a 6.0x offensive clamp. Rewrite FirstAid to ScalingFormula (Log-Sigmoid like other skills) contributing at most ~a few hundred HP toward the cap. Enforce both ceilings as hard clamps at resolve time in PlayerVirtualHealthManager and CombatSkillProcessor, not as advisory targets. |
| P0 | Resolve the mob HP-cap collapse. healthCap is hardcoded-default 5000 (combat.yml health-cap: 5000.0). At base-health 20 + 6/level * tier-mult, PRIMORDIAL (60x) hits 5000 at ~level 12, MYTHIC (25x) ~level 31, PERFECT (16x) ~level 50 — so the top four tiers are visually identical sponges across the whole midgame. Choose: (a) raise the global cap (~25k-40k), (b) per-tier health-cap map (recommended), or (c) keep 5000 and differentiate top tiers only via armor-pen/abilities. | This is the most-cited landmine across four domains (Bestiary, World, Endgame, Gear). It blocks ALL endgame mob authoring and gear calibration: gear WP/AP budgets are tuned against this curve, and Bands 6-9 / top tiers are indistinguishable until it is fixed. | Per-tier health-cap map (option b): it preserves the existing field, needs no new resolution code, and lets each tier flatline at a distinct ceiling. Pair with the Threat-tier override for instanced endgame (separate cap). Defer the global-25k idea unless you also commit to the higher player HP ceiling. |
| P0 | Set the weapon base-damage anchor: the exact COMMON reference base damage for a sword (design assumes 7.0, matching diamond). combat.yml currently has no weapon-base section. Also decide whether the WP/AP budget keys off Tier.craftStatMultiplier (0.5x..4.0x) directly. | This single number anchors the entire weapon-power budget; every affix, temper, reforge, and infusion number is expressed relative to it. Without it, no gear stats can be authored and DPS/time-to-kill cannot be computed against the mob curve. | Lock COMMON sword base = 7.0, add a weapons base-damage section to combat.yml, and derive per-tier base = 7.0 * craftStatMultiplier as the starting budget. Confirm intended time-to-kill vs a level-matched RARE mob (proposed ~4s) so the budget has a target. |

## Gaps Nobody Flagged (surfaced by the completeness critic)

- MONETIZATION STANCE (nobody surfaced this; it silently constrains every economy decision). Decide now whether this is a pure-cosmetic / no-monetization private server, a donation-perk server, or a pay-for-convenience server. This is legally load-bearing on Minecraft: Mojang's EULA forbids selling gameplay advantage. The three-currency economy, bind-on-pickup bands, Inventory Badge, and prestige all change shape depending on whether premium currency can ever be bought. If any real-money element is planned, Echo Shards as a 'family-premium' currency is an EULA red flag. RECOMMEND: declare cosmetic-only monetization explicitly and design Echo Shards as strictly earned, not purchasable.
- SAVE-DATA SCOPE, MIGRATION & WIPE POLICY (the design adds many new tables — player_echo, player_inventory_badge, player_pity, currency wallets, player_pvp_rating, warbands, descent_depth, leaderboards, discovered_gates, escrow — but nobody owns the schema-migration story). Decide: is there a versioned migration path for the SQLite schema as columns/tables are added, what happens to existing player data when the XP curve and FirstAid HP are rewritten (every saved skill level now means a different power level), and is there a planned wipe at 'v1 launch'? Also: SQLite vs a real DB if the server ever scales past single-instance. RECOMMEND: add a schema_version table now, write idempotent migrations, and plan a clean wipe at the first real launch since the FirstAid/HP rewrite invalidates all current saves anyway.
- MULTIPLAYER SCALE & PERFORMANCE BUDGET (assumed 'likely small population' throughout, but never decided). The whole design — distance-based leveling, roaming sea monsters, persistent elites, per-chunk traps, Folia regions, instanced Depth worlds — has very different perf characteristics at 5 players vs 50 vs 200. Decide the target concurrent-player count and the per-tick entity/scaling budget. This determines whether plugin-spawned elites can persist, how many gates/POIs can exist, and whether instanced raid worlds (cerb_depths) are even affordable on the host. RECOMMEND: pin an explicit target (e.g. 20-40 concurrent), and load-test the spawn/scaling listener and Folia region thread-safety against it before authoring content.
- SCOPE-CUT / MVP DEFINITION & BUILD ORDER (the planners produced an enormous feature surface but no one defined the minimum shippable v1 or the dependency-ordered build sequence). The constraints note 99 modified + 18 new files are uncommitted and must be committed before major work — so step zero is repo hygiene, not features. Decide the v1 cut line. RECOMMEND v1 = (1) commit current work + delete the Creb/ nested-repo + git rm --cached target/, (2) fix the three P0 math landmines (XP curve, FirstAid HP, mob HP cap), (3) ship Bands + Families + Blink Gates with config-only mobs, defer Outpost Sieges, Contracts, Spaceman Armor, and the full Endgame/Threat layer to v2. Without this line drawn, the project stays in permanent planning.
- DOC & SOURCE-OF-TRUTH HYGIENE (CLAUDE.md and AI_HANDOFF.md are stale — they reference Paper 1.21.1, DecentHolograms, region management, and DB assumptions that no longer hold; the design baseline says Folia 1.21.11 and region system removed). A shipping project needs one authoritative design doc. RECOMMEND: after the Open Decisions above are answered, write a single canonical balance-constants doc (HP/damage caps, XP curve params, tier multipliers, currency rates) that combat.yml and code comments point to, and update/delete the stale handoff docs so future sessions don't act on dead assumptions.
- BUILD/RUNTIME FRAGILITY — the --enable-preview pin (Java 21 preview features). The constraints flag that preview API usage makes the build pinned to exactly JDK 21 and adds runtime/build pain, and question whether preview features are genuinely needed. This is a shipping risk: a server admin on JDK 22/23 cannot load the plugin at all, and preview APIs can change between JDK builds. DECIDE whether to audit and remove the preview dependency. RECOMMEND: grep the actual preview-feature usage; if it is incidental, drop --enable-preview to widen JDK compatibility and remove a whole class of deploy failures.
- ACCESSIBILITY & UX READABILITY (custom HUD, floaty damage numbers, defense bar, Echo Compass, Band names all render through PlayerHUDManager, but no one addressed colorblind-safe tier colors, text-size/scaling, or info overload). The Tier enum hardcodes colors (e.g. RARE=blue, EPIC=dark_purple) that are hard to distinguish for colorblind players, and the HUD stacks health+mana+defense+combo+damage numbers. RECOMMEND: add a tier-symbol/prefix in addition to color, and a config toggle to reduce HUD density; decide this before the GUI/HUD work expands further.
- CONTENT CADENCE & LIVE-OPS OWNERSHIP (seasonal Reservoirs, Family Wars, and leaderboards imply ongoing operation, but nobody decided who authors new mobs.yml entries / seasons or how often). A season system with no content pipeline dies after season 1. RECOMMEND: decide whether seasons are hand-authored (and at what cadence given solo-dev bandwidth) or procedurally varied; if bandwidth is the constraint, lean on the random-affix elite layer and procedural Depth Spiral floors as the primary 'new content' source rather than hand-authored seasons.
- GRIEFING, ANTI-CHEAT & MODERATION SURFACE (PvP, ManaDrain-vs-players, trap placement, ritual-interrupt, and the escrow/Contracts system each open an exploit/grief vector, but there is no consolidated moderation/abuse policy). Decide: trap/ManaDrain legality per zone, escrow dispute resolution, and protection against the distance-leveling exploit (relogging at far coords, or being TP'd deep). RECOMMEND: centralize all PvE/PvP/trap legality checks in the ZoneManager so there is one enforcement point, and require the Blink-Gate USE-gating (already in Open Decisions) specifically as anti-exploit, not just pacing.
- TESTING & BALANCE-VERIFICATION STRATEGY (only HealthLifecycleEngine and MobHealthScaling have unit tests; the riskiest new math — XP curve, combat multiplier clamp, defense pipeline order, inversion swap — has none). Every P0 number above is a regression risk. RECOMMEND: add unit tests for the rewritten XP curve (assert monotonic, no overflow, hits target cumulative at 100), the player HP/damage clamps, and the 3-layer defense order, BEFORE wiring new systems on top of them — these are pure functions and cheap to test, and they are exactly the values that will silently drift.

## Appendix — Per-Domain Open Questions

### Bestiary & Mob Types

- HP cap landmine: which fix do you want — raise the global cap to ~40k, add a per-tier health-cap map (recommended), or keep 5000 and differentiate elites via armor-pen/abilities only? This decides whether your top four tiers are distinguishable in the endgame.
- Should the mob damage cap stay at 10x (currently unreachable — PRIMORDIAL L100 only hits 8.48x) or be lowered to ~9, or should PRIMORDIAL's tier-base be raised so the ceiling is meaningful?
- How do non-Monster mobs (Slime, Ghast, Phantom, Hoglin, Shulker) scale? Pick: stay on apply-to:MONSTERS and never use them as scaled mobs, switch to ALL (scales passive animals too), or build a curated entity-type allowlist in MobHealthScaling.
- Should mob level get a biome/Y-depth modifier on top of horizontal distance, or stay pure-distance? Pure distance means deep-dark-at-spawn is level 1 and there's no danger signposting.
- Per-world blocks-per-level: should the Nether/End use a different value (the 8:1 compression makes Nether mobs level 8x faster) or share the overworld 150?
- Boss HP model: fixed per-tier cap, or scale boss HP with nearby player count / use DPS-gate phases so solo players aren't fighting a multi-minute sponge?
- Do you want a random-affix/elite layer (Vampiric, Volatile, etc.) between named bosses and generic mobs, or only hand-authored named mobs?
- Family token drops: only from same-family mobs (recommended for Echo Families progression) or any mob in that family's biome regardless of the mob's own family?
- Does mob XP feed all 30+ skills, only combat/magic skills, or a configurable set — given PRIMORDIAL's 15x XP and the intent to farm far-out mobs?
- Despawn policy for named/plugin-spawned elites: leash-radius despawn, time-to-live, or persist forever (risking chunk leak)?

### Weapons & Gear

- Delete the duplicate Quality enums in CraftingManager and QualityBuffs and migrate both to the unified Tier enum? (They contradict the 10-tier system and use different multipliers — 3.5x vs 4.0x.)
- What is the exact COMMON reference base damage for a sword? The design assumes 7.0 (matching diamond) but combat.yml has no weapon-base section yet — this single number anchors the entire WP budget.
- Should weapon damage use a separate vs-player scalar for PvP (proposed ~0.25x), and at what value, given gear is tuned against 5000-HP mobs but players have 100 HP?
- Hard per-item power ceiling: what is the absolute max WP/AP an item can reach after reforge + temper + affixes + infusion stacking, and is it clamped at resolve time?
- Crit affix stacking rule: do Keen/Savage affixes add to the Critical Strike roll BEFORE the single roll (capped at 0.75) or multiply after? This determines whether crit chance can be pushed to ~100%.
- Temper cap: how many tiers above its craft tier can an item be upgraded (proposed +3), and what are the tier-shard material costs per step?
- Should Spaceman Armor be a fixed GODLY-equivalent stat set or purely cosmetic with no combat stats? (Affects whether it competes with endgame keyed sets.)
- Are keyed-armor set bonuses fully inert for non-attuned players, or do they grant a reduced (e.g. 50%) bonus? This gates how punishing family commitment feels.
- Entropy curve: is the 50%-power-at-full-entropy floor correct, or should some items (Nomicons) be entropy-immune?
- Which mob tiers populate the Nomicon drop pool, and is Nomicon acquisition drop-based or strictly quest-based (the design splits them — bosses drop, quests grant)?

### Progression, Economy & Itemization Loops

### Core Gameplay Loops, Player Fantasy & Balance

- **Tier power ratio:** pick the exact per-step multiplier (e.g., 1.30× vs 1.40×) for the 9 tier steps — sets the entire economy's slope.
- **Skill diminishing-returns curve:** choose the formula/`k` (exponential vs tiered step table) and each skill's hard-cap contribution to its stat budget.
- **Defensive budget cap:** set the global max total damage reduction (e.g., 70% vs 80%) that armor + resist + bar + skills clamp to.
- **TTK targets per band:** lock the intended kill time and survival margin per distance band, and the mob-level → distance mapping resolution.
- **Virtual Health budget:** decide the capped HP range across levels (hundreds vs low-thousands) now that flat-per-level grants are banned.
- **Defense-bar tuning levers:** finalize base size, drain rate, regen rate, and the 7s out-of-combat threshold per tier — the primary TTK dials.

- **Blink Gate cost curve:** how gate placement/use cost scales with destination band, and whether under-geared players are soft-blocked from far gates.
- **Specialization pressure:** is there an explicit cap on simultaneously "maxed" skills, or is time the only limiter? (Affects build identity strength.)
- **Reservoir Inversion balance:** how swapping HP/MP interacts with the capped budgets and the defense bar (does inverted HP still feed bar overflow?).
