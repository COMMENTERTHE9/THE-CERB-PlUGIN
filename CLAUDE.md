# Claude Code Memory — Cerberus Plugin

## Project
Minecraft RPG plugin — cultivation / xianxia-flavored but **Western-named** — with a deep skill / combat / progression system. Currently mid-build: the full design is complete (`docs/design/`) and Step-0 foundation code is underway.

## Tech
- **Main class:** `cerberus.world.cerb.CerberusPlugin`
- **Platform:** **Folia 1.21.11** (region-threaded — entity/player ops must run on the owning region thread; no main thread; use `teleportAsync` for cross-region; **NO ProtocolLib**)
- **Java:** 21 (`maven.compiler.release=21`; no preview features). Any JDK **>= 21** builds it (21 and 25 verified) and Folia 1.21.11 runs on Java >= 21.
- **Build/run:** see `RESTART_GUIDE.md`. `run.bat` = build + back up plugin data + deploy + start; `status.bat` reports Java/server/worlds/running state. Logic lives in `tools/cerb.ps1` (Windows) and `tools/cerb.sh` (Linux/macOS). Tests: `.\mvnw.cmd test`.
- **DB:** SQLite, async via `AsyncSaveManager` (6 tables auto-create on startup; `player_classes` holds one versioned classes document per player)

## Design (read this first)
The full game design lives in **`docs/design/`** — start at **`docs/design/README.md`** (index + build-readiness status). The owner's decisions, each with its state: **`docs/DECISIONS.md`** (check it before asking the owner anything; never ask a settled question again). The owner's current priorities and build order: **`docs/ROADMAP.md`** (performance first; multiclass ability trees with cross-class loadouts are the next big design area). Doctrine: **controlled hyperscaling** (cultivation-scale numbers into the billions/trillions, realm suppression) + **Western-forward naming** (`NAMING.md`: Mortal…Primordial realms layered over the 10-tier `Tier` enum). Everything new is a **data-driven registry** (mirrors `MobRegistry`): config, not code.

## Conventions
- **Respect the player's time** (owner, 2026-10-27, permanent; `docs/DECISIONS.md`): automation is acceptable; exploiting bugs, duplicating items, destroying the economy or harming server performance is not. AFK play, macros for ordinary actions and clever farms earn the normal rewards. Never add inactivity timers, anti-macro detection or movement/interaction challenges. A reward may be withheld only when nothing really happened (placed-and-broken blocks, creative, admin tools, fabricated or cancelled events), for loops that make value from nothing (duplication, double refunds), for server protection (entity limits, bounded work), or by pacing that applies equally to active and passive play. Active play earns *more* (challenges, discoveries, encounters), passive play is never made worthless.
- **Performance first:** every significant milestone starts by measuring a reproducible baseline for the systems it touches (`tools/playtest/load.js` + `tools/perf/profile.sh`, method in `docs/PERFORMANCE.md`), fixing confirmed bottlenecks, and measuring again. No speculative rewrites. Menus: change screens with `MenuManager.open/replace` (same-size screens redraw in place); never open raw inventories per click. A screen whose buttons change state at once returns `reuseWindow() = false` (all admin screens do) so stale clicks can't reach it.
- **Movement abilities come back in 1.2 s at most** (owner rule, 2026-10-25, standing): every dash or blink and the lockout they share; teleport-style movement may be as quick as the 0.4 s cast gap. Enforced in `ClassCatalog` (`MOVEMENT_MAX_COOLDOWN_MS`); a strike or stun on a movement ability may keep a slower `strike-cooldown`.
- **Shipped config on older installs:** `abilities.yml`/`classes.yml` written at install are refreshed at startup only when unedited (`ShippedConfig`; the old copy kept as `.old`, `.old.2`…, never overwritten). Changing one makes `ShippedConfigTest` fail until the old version's hash is recorded. Other config changes need a code default that old files fall back to.
- **PvP is off for now, not permanently** (owner, 2026-10-25): every PvP limit (attributes, speed bonuses, abilities, class XP) is temporary, waiting for a PvP pass that turns it all on. Keep each one switchable and listed in `docs/ROADMAP.md` → PvP; never treat them as final design.
- **Folia threading:** snapshot on the entity/region thread → async I/O → reschedule back. Never touch Bukkit entity/player APIs off-thread.
- New content ships as **config** (mobs.yml / combat.yml / *.yml + a registry), not code.
- Pure-function math (curves, formulas) must have **unit tests**; run `mvnw.cmd test` (any JDK >= 21).
- Verify gameplay changes on a running server, not just the build. In a cloud/Linux session, `tools/cerb.sh` can download Folia and run a local test server (see RESTART_GUIDE.md).
- Commit working increments; keep the tree clean.
- **Shipped config files** (`abilities.yml`, `classes.yml`, `attributes.yml`, `resources.yml`) are refreshed at startup when unedited (`ShippedConfig`): when you change one, add its old hash to `ShippedConfig.EARLIER` and the new one to `ShippedConfigTest` (the test says so).
- **Every skill improves at least one meaningful attribute or secondary stat** (owner rule, 2026-10-26, permanent), through the one attribute engine (no per-skill stat managers, no filler bonuses); the design for all 35 is `docs/design/SKILL_PROGRESSION.md`, built with each skill's own gameplay.
- **Progress shown to a player** (a level, a rank, a new ability; later realms, trials, Awakenings) goes through `Skills.Celebrations` as a `Celebration`: one presentation per moment, effects rate-limited, vanilla sounds and particles only. Admin tools and data loading change numbers quietly (`SkillManager.addXpQuietly`, `ClassService.addXpQuietly`/`setRank`).
- **XP withheld on purpose says why** (owner report, 2026-10-27): a source that withholds XP by rule (creative, an origin with share 0) calls `SkillManager.xpWithheld(player, skill, why)`, shown by the XP display at most once per skill and reason every 5 minutes; never silently. Every skill starts at level 1 (`SkillProgression.MIN_LEVEL`).
- **Anything that pays XP for an action** counts what really happened (the game's statistics, the final event state at MONITOR), never the click or the attempt; and it has a negative and a positive control in a harness. A load that pays XP (`load.js`) sets the skill level it starts from, so before/after runs do the same work.
- **Effects that change many blocks** (Felling, later vein mining or area tools) run in bounded steps on the region thread that owns the blocks, re-check ownership, type and the placed-block memory at every step, offer each block to protection plugins as the player's own break (`Woodcutting.FellingBreak`) and stop at the first refusal; they never touch another region's blocks or an unloaded chunk.
- **New entries in a shipped config** reach servers whose file has edits: list them in the file's `ADDED_BY_UPDATES` (`AttributesConfig`, `GatheringCatalog`), so they are read from the plugin's own file when the server's doesn't mention them; the owner's file on disk is never rewritten. Combat XP goes through `Manager/XpIntegrity` (origin share, creative, per-mob budget); harnesses that measure kill or class XP run in survival.
